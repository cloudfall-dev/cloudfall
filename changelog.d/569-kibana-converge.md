### Added

- `services.yml` converges a Kibana service (S-024) with the new `cloudfall_kibana` role, on loopback and without a `domain`: in a play of its own, once every node of its cluster that the run converges has finished, it installs `kibana=<version>` of the Elasticsearch service from the node's Elastic repository and holds it, writes `/etc/kibana/kibana.yml` (`server.host`, `server.port`, `server.publicBaseUrl`, `elasticsearch.hosts`, the project CA with the node's `remoteAccess`, `telemetry.optIn: false`) and the declared heap into `/etc/kibana/node.options`, creates a token of the `elastic/kibana` service account named after the Kibana service in that node's `service_tokens` file, and puts the token and the three encryption keys in Kibana's keystore, never in a file a person reads. Each is put once: a second converge changes nothing and restarts nothing. The role waits until Kibana reports itself available at the service's version, and stops the converge when it does not, when the node holds no such token, when an unauthenticated request for a dashboard is not sent to the login form, or when Kibana listens outside loopback. A `heapMb` that with the node's heap is above three quarters of the server's memory stops the converge before any task changes the server, and so does a Kibana of another version than the cluster's; a declared `domain` is refused until a release publishes Kibana. The kind yields its S-011 requirements: the `kibana` package and three `generate` secrets (`kibana-security-encryption-key`, `kibana-saved-objects-encryption-key`, `kibana-reporting-encryption-key`, under `/services/<id>`), which `cloudfall secrets generate` makes and the services converge stages, failing before any playbook when one is missing. The `kibana_system` password is never set or changed (#569)
