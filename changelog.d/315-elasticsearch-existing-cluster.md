### Added

- An Elasticsearch service with `existingCluster` is converged instead of refused: its nodes join a cluster Cloudfall did not create (S-012). Each node's transport leaves loopback even when it is the only Cloudfall node: `discovery.seed_hosts` lists the existing cluster's seed hosts, then the Cloudfall nodes; its firewall admits 9300 from the other Cloudfall nodes and the seed hosts' addresses only; it gets its transport certificate from the project CA and trusts the existing cluster's `caCertificateFile` beside it, which the services converge delivers to `/etc/elasticsearch/certs/existing-cluster-ca.crt`, with `verification_mode: certificate`. A joining node never writes `cluster.initial_master_nodes` and never sets the `elastic` password, which stays the existing cluster's, and the existing nodes are only read. Before the data volume and the package, the role asks the seed hosts over HTTPS on port 9200, verified against that CA and as the `cloudfall` account (which the team grants the `monitor` privilege on the existing cluster), for `GET /_nodes`, and stops, naming the seed host or node and its value, when the cluster's name differs from `clusterName`, when a node runs another major, when a node is newer than `version`, or when no seed host answers. Once `existingCluster` is removed, a converge drops the seed hosts and the CA from the configuration, restarts one node at a time, removes the CA file, and waits for the cluster to be green (yellow with one node); `clusterName` keeps the name. `config validate` refuses a seed host given by name rather than address, and a node that joins an existing cluster without a firewall or an IPv4, as for a node of a cluster of two or more (#315)
