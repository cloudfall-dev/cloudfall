### Added

- A MariaDB service is backed up and its restore drilled (S-019): `services` installs `cloudfall-mariadb-backup` and `cloudfall-mariadb-restore-check` with their systemd timers (the drill's only with `restoreCheckOnCalendar`), run as root through the socket, and `cloudfall backup run <service>` and `cloudfall backup verify <service>` run them and write their `BackupReceipt`. A backup writes, for every declared database, one gzip dump taken with `mariadb-dump --single-transaction` (one consistent snapshot of the InnoDB tables, no table locks; tables of another engine are named in the output) and beside it a count file of every table and its rows, counted from the stored dump, both `0600` in a `0700` directory; then it deletes each database's dumps older than `retentionDays`, never the newest, and only files of the names it writes. The drill loads the newest dump of each database into the scratch database `cloudfall-restore-check` without writing to the binary log, compares its tables and row counts with the count file (never with the live source, so later writes cannot fail it), and drops it on every path; it fails, and says so, when a database has no dump or no count file, when the load fails, and on any difference, and leaves a database of the scratch name it did not make alone. The role checks `onCalendar` and `restoreCheckOnCalendar` before it changes the host. The dumps hold tables, views, routines and triggers but no scheduled events (`--events` is not passed, so no event can run in the drill's scratch database): a team that uses events recreates them after a restore (#422)
