### Added

- An Elasticsearch service grows to two or more `nodes` and rolls a version one node at a time (S-012). Each node yields an `elasticsearch` data volume of 10 GiB at `/var/lib/elasticsearch` in its baseline's only storage pool, `mirrored` for a cluster of one and `expendable` for two or more; a node of a cluster of two or more also yields port 9300/tcp open to the other nodes only and an `elasticsearch-transport` certificate from the project CA for its hostname and addresses, of the usage `server-and-client`: the one certificate `remoteAccess` serves HTTP with, which the services converge now issues for a node with `remoteAccess` too. The role refuses `remoteAccess` on a cluster of two or more, since its one `listenAddress` exists on one server only. `config validate` refuses a node whose baseline has no pool (`volume_requirement_pool_missing`), several (`volume_requirement_pool_ambiguous`), or, for a cluster of one, no secondary physical volume (`volume_requirement_pool_unmirrored`), and a node of a cluster of two or more with no IPv4 (`service_elasticsearch_node_unaddressed`). The rendered inventory carries the service on every node with its transport address and seed hosts, adds the 9300 rule to each node's firewall, and lists each cluster's home first. Every path that runs `services.yml` through `cloudfall` first reads each node's volume facts and decides its volume, then has each node make its key and a signing request, signs the missing and due certificates with the project CA and delivers them, all before any host changes. The role creates and mounts the volume, enforces the firewall, binds the transport to the node's address with TLS `verification_mode: full`, bootstraps a cluster only from the home node and refuses when another node of it already runs, sets the `elastic` password from the home only, and restarts a running node only from a green cluster (yellow with one node), with replica allocation held and a flush (released again even when the restart, the rejoin or the version check fails), then waits for the node to rejoin on the declared version and the cluster to return to its status before the next server (#312)
- An Elasticsearch service's S3 `snapshotRepository` is converged instead of refused (S-012). Its `credentialsRef` names one key of the secret store holding `<access key id>:<secret access key>`; every path that runs `services.yml` decrypts it on the controller, stages the two keys in 0600 files and passes only their paths, and stops before any playbook when the key is missing or malformed. On every node the role puts them in the keystore as `s3.client.default.access_key` and `s3.client.default.secret_key` through stdin, keeps only their SHA-256 beside it so a second converge changes nothing, names the endpoint as `s3.client.default.endpoint` in `elasticsearch.yml`, reloads a running node's secure settings, and registers the repository `cloudfall` as `type: s3` with the bucket and base path, replacing the filesystem repository of a service that grew; the snapshot and restore-drill scripts use it unchanged (#312)
- `config validate` refuses an Elasticsearch cluster of two or more nodes on a baseline without a firewall, since nothing would narrow 9300 to the other nodes (`service_elasticsearch_cluster_firewall_missing`); the inventory render refuses it too (#312)

### Changed

- A `mirrored` volume now meets an `expendable` requirement (D-18): when a one-node Elasticsearch service grows, its first node keeps its raid1 data volume, and the volume provider keeps and grows it, and `audit` checks it, as the mirror it is; a linear volume still never meets a `mirrored` requirement (#312)
- When installing a new Elasticsearch version fails after the node was stopped for it, the role starts the node again on the package it had and lets its cluster move replicas again before the converge stops (#312)
