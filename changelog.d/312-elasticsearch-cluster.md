### Added

- An Elasticsearch service grows to two or more `nodes` and rolls a version one node at a time (S-012). Each node yields an `elasticsearch` data volume of 10 GiB at `/var/lib/elasticsearch` in its baseline's only storage pool, `mirrored` for a cluster of one and `expendable` for two or more; a node of a cluster of two or more also yields port 9300/tcp open to the other nodes only and an `elasticsearch-transport` certificate from the project CA for its hostname and IPv4, of the new usage `server-and-client`. `config validate` refuses a node whose baseline has no pool (`volume_requirement_pool_missing`), several (`volume_requirement_pool_ambiguous`), or, for a cluster of one, no secondary physical volume (`volume_requirement_pool_unmirrored`), and a node of a cluster of two or more with no IPv4 (`service_elasticsearch_node_unaddressed`). The rendered inventory carries the service on every node with its transport address and seed hosts, adds the 9300 rule to each node's firewall, and lists each cluster's home first. Every path that runs `services.yml` through `cloudfall` first reads each node's volume facts and decides its volume, then has each node make its key and a signing request, signs the missing and due certificates with the project CA and delivers them, all before any host changes. The role creates and mounts the volume, enforces the firewall, binds the transport to the node's address with TLS `verification_mode: full`, bootstraps a cluster only from the home node and refuses when another node of it already runs, sets the `elastic` password from the home only, and restarts a running node only from a green cluster (yellow with one node), with replica allocation held and a flush, then waits for the node to rejoin on the declared version and the cluster to return to its status before the next server (#312)
