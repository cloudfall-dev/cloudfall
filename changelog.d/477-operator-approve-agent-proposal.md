### Added

- `cloudfall operator approve <id>` now runs an agent's proposal (one a confirmed `cloudfall mcp serve` call no grant covered left in the proposal store) instead of refusing it with `operator_agent_proposal_unsupported`. As for the operator's own proposals, a person types the id at a terminal (`PERSON_REQUIRED` off one, and nothing runs). The command then recomputes the plan of the stored tool call, the git commit and the digest of uncommitted changes outside `decisions/`, `record/` and `tmp/`, and refuses any difference before anything runs with `PRECONDITION` and `context.code: proposal_binding_changed`, naming what changed in `context.changed`; the proposal stays `proposed`, and the agent calls the tool again for a new one. Otherwise the stored call runs through the tool's own command, S-008's release approval included, recorded with `approval.mode: human` and `via: terminal`, and settles `verified` or `failed` by the tool's own check (the health gate, every migrate step, the copy's receipt, `domains observe`, or an `audit` of the changed servers). A verified person-approved run counts toward the `requiredVerifiedRuns` of the policy grant for its class in its environment. `cloudfall operator run` still leaves agent proposals `proposed`, listed as withheld because only a person approves them. `operator approve` lists `CONFLICT` and `PARTIAL_FAILURE` among its exit codes, which a stored `deploy`, `rollback`, `restart` or `migrate` can end with (#477)
