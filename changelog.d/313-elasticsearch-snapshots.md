### Added

- `cloudfall backup run` and `cloudfall backup verify` work for a `serviceKind: elasticsearch` service (S-012). The converge adds `backup.directory` to `path.repo`, registers it as the filesystem snapshot repository `cloudfall`, and installs `cloudfall-elasticsearch-backup` and `cloudfall-elasticsearch-restore-check` with sandboxed units and timers on `backup.onCalendar` and `backup.restoreCheckOnCalendar`. The backup takes the snapshot `cloudfall-<timestamp>` of every index and the cluster state, waits for it, fails unless its state is `SUCCESS` (so a `PARTIAL` or `FAILED` snapshot writes no receipt), records in the snapshot's metadata the document count of each index the drill restores (`restoreCheckIndices`, or the smallest index), and then deletes Cloudfall's snapshots of the service older than `retentionDays`, always keeping the newest and never touching a snapshot it did not take. The restore drill verifies the repository, checks the low disk watermark, restores the recorded indices of the newest snapshot as `cloudfall-restore-check-<index>` with no replicas and without aliases, waits for green, compares the document counts, and deletes the restored copies even when a step failed; it refuses to start when an index of a copy's name exists, and fails when no snapshot exists. Both run as the `elasticsearch` user and write the usual `BackupReceipt`; an S3 `snapshotRepository` stops the converge until its keystore keys are converged (#313)
