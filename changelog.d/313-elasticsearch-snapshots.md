### Added

- `cloudfall backup run` and `cloudfall backup verify` work for a `serviceKind: elasticsearch` service (S-012). The converge adds `backup.directory` to `path.repo`, which restarts each existing node once on the first converge after the upgrade, registers it as the filesystem snapshot repository `cloudfall`, and installs `cloudfall-elasticsearch-backup` and `cloudfall-elasticsearch-restore-check` with sandboxed units and timers on `backup.onCalendar` and `backup.restoreCheckOnCalendar`. The backup counts the documents of every index `restoreCheckIndices` matches (or of the smallest index) and writes the counts as one document per snapshot into Cloudfall's own index `cloudfall-snapshot-counts`. It then takes the snapshot `cloudfall-<timestamp>` of every index, that one included, and the cluster state, waits for it, and fails unless its state is `SUCCESS`, so a `PARTIAL` or `FAILED` snapshot writes no receipt. Finally it deletes Cloudfall's snapshots of the service older than `retentionDays` with their counts, always keeping the newest and never touching a snapshot it did not take. The restore drill verifies the repository, restores the snapshot's counts and every recorded index as `cloudfall-restore-check-<index>` with no replicas and without aliases, checks the low disk watermark, waits for green, compares each document count, and deletes the restored copies even when a step failed; it refuses to start over an index of a copy's name, and fails when no snapshot exists. Both run as the `elasticsearch` user and write the usual `BackupReceipt`. An S3 `snapshotRepository` stops the converge with a message that S3 repository registration is not built yet (#313)
